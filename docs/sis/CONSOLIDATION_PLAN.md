5. **One move per session, one session per worktree.** The status table below is
   updated by the session that ships the move, the way `ROLE_CAPABILITIES.md` is
   regenerated by whoever moves a route.

## How a move is executed

Every move follows the same shape, and the shape is most of the safety.

1. **Worktree, not the shared checkout.** `git worktree add ../pw-<move> -b
   consolidate/<move>-<slug>` from `main`. Several sessions edit the main checkout at
   once; a move that touches thirty files must not do so there.
2. **Read the audit section for the move first**, then the manifest row(s) it lowers.
   The manifest's failure message says what the canonical thing is; the audit says
   where every copy lives.
3. **Schema before query.** Any move with a migration checks the live schema over the
   Supabase MCP before writing SQL (CLAUDE.md rule 3), and lands the migration file
   in `supabase/migrations/` with the additive-only shape the folder expects.
4. **Lower the baseline in the same commit as the merge.** A move is not done while
   the manifest still says the old number. `RATCHETS.md` §1 gets the same edit.
5. **Verify at http://localhost:3000 as iCreate and as one other org** (Gryffin for
   family-facing moves, Arete for kiosk or class moves, Optio Academy for anything
   touching the funnel or recurring tuition). The verification list in each move is
   the minimum; the user confirms at the browser, not at a green test.
6. **Full suites before the commit**: `cd backend && pytest`, `cd web && npm run
   test:run`, and `cd mobile && npm test` when mobile is touched. Zero failures.
   `docs/sis/ROLE_CAPABILITIES.md` is regenerated if any route changed tier
   (`python backend/scripts/dump_role_matrix.py`).
7. **Commit only the move's files**, with the status line in this document updated.
   Push to `develop` deploys dev. `main` is production and the push is asked for,
   never assumed.

### What lands

**`shared/sisConcepts.json`** — the concept manifest. Same role as
`shared/roleCases.json`, which one pytest, one vitest and one jest suite already read,
so the path resolution and the "fixture is the source of truth" convention exist.
One entry per concept:

```json
{
  "id": "invoice_row",
  "means": "A row in sis_invoices. Every charge a family sees, whatever created it.",
  "owner": { "backend": ["services/sis_billing_service.py"] },
  "forbid": {
    "backend": { "pattern": "\\.table\\(\\s*['\"]sis_invoices['\"]\\s*\\)\\s*\\.insert", "dirs": ["routes", "services", "repositories", "utils", "jobs"] }
  },
  "baseline": { "backend": 3 },
  "measured": "2026-09-17",
  "lowered_by": "M6",
  "use_instead": "sis_billing_service.create_charge(org_id, household_id, lines=..., kind=..., source=...). It is the one row writer; pass lines, do not insert."
}
```

Fields: `owner` paths are excluded from the count unless the row says `exempt: []`
(the canonical copy matches its own pattern and counts; the target after the move is
one). `forbid.<side>.pattern` is a regular expression applied line by line, after
comments and docstrings are blanked, to files under `dirs` (backend: relative to
`backend/`; web: relative to `web/src`; mobile: relative to `mobile/`; a `dirs` entry
may be one file, or a prefix like `services/sis_`). `files` lists paths whose mere
existence counts one each; `unit: "files"` counts files with a match instead of lines.
Test files are never scanned. `baseline` is per side and may only fall. `use_instead`
is the sentence the failing test prints — it is the documentation a session reads at
the moment it is about to add a copy. `lowered_by` names the move. An owner that does
not exist yet (`services/sis_holds.py`) carries `"proposed": true`; the freshness test
skips its existence check until the move ships, and fails once every owner exists
and the flag is still there.

**`backend/tests/unit/test_sis_concepts.py`** — parametrized over every manifest entry
with a backend pattern. Three assertions per entry, in the house style of
`test_direct_db_calls_do_not_grow.py`:

- *ceiling*: matches outside the owners `<= baseline`; on failure, print every
  offending `path:line` and the entry's `use_instead`.
- *floor*: matches `>= baseline`, so with the ceiling the count is exact — a scan
  that stops matching passes forever, which RATCHETS.md forbids, and slack below the
  real number is the fraction of a fix that can be undone silently. A copy that was
  genuinely removed lowers the baseline in the same commit; the message says so and
  names the number.
- *freshness*: `measured` is a date; owners exist on disk unless `proposed`, and a
  `proposed` row whose owners have all arrived fails until the flag is removed.

Plus `test_the_scan_reads_real_files` (the walk finds the tree, the stripper keeps
the code) and `test_comment_stripping_rules` (the rules stated as a fixture), the
guard-on-the-guard the repository already uses.

**`web/src/__tests__/sisConcepts.test.js`** — the same assertions for web patterns,
in the style of `brandPalette.test.js`; reads the same JSON. The comment rules and the
file walk live in `web/src/tests/sourceScan.js`, shared with the two bespoke tests
below. **`mobile/src/__tests__/sisConcepts.test.ts`** does the same for the one row
with a mobile pattern (the client-side feed merge), in the style of
`schoolEventWallClock.test.ts`.

**Two bespoke tests**, where a count is not the right shape:

## What the guards cannot do, stated once

The manifest freezes every duplicate the audit named and makes a new copy of a
*known* concept fail the build with a sentence that says what to use instead. It
does not know a concept nobody has named. A session can still build a second
"training" under a name the manifest has never seen. The skill steps narrow that
window — search the manifest for the noun before building; add a row to declare a
new concept — and the reviewer sees the declaration. That is a large improvement
over prose, and not a guarantee.
