## The headline: the drift is far smaller than the ticket says

The brief for this work described "73 files in `supabase/migrations/`, 96 rows in
`supabase_migrations.schema_migrations`, overlap of 5" — and asked for the 67
files with no history row and the 91 applied versions with no repo file.

**Those two numbers are an artifact of joining on the version string, and they
overstate the problem by roughly twenty times.** Joining on version asks "does a
row exist whose `version` equals this filename's stamp". Almost every migration
here reached production by hand, and hand-application stamps the history row at
*apply* time while the filename was written earlier that day. So the same
migration appears on both sides under two different numbers and the join misses
it.

Matching on migration *name* and then diffing the recorded SQL against the file
gives the real picture:

| | Count | Meaning |
|---|---:|---|
| `.sql` files in `supabase/migrations/` | 72 | 73 directory entries; one is `README.md` |
| — matched to a history row at the **exact** version | 5 | |
| — matched by **name**, history row carries a drifted stamp | 64 | Same migration, recorded under a later timestamp |
| — **no history row under any name** | 3 | |
| History rows | 96 | |
| — with no repo file | 27 | 26 pre-date the baseline and live in `migrations-archive/`; **1 does not** |

**Every one of the 72 files is already applied to production.** Nothing in the
repo is a pending schema change waiting on a decision. The tables below say so
file by file, and the seven cases where the recorded SQL could not settle it were
checked against the live schema directly.

So the entire problem is bookkeeping. That is good news and it is also the
danger: `supabase db push` compares file stamps against `schema_migrations.version`
and nothing else, so today it would attempt **66 migrations that already ran**.
Some are `IF NOT EXISTS`-guarded. Not all are. This is exactly why
`migrate-prod.yml` refuses to apply above `max_pending`.

## What the baseline does and does not contain

Generated by [`scripts/dump_prod_schema.py`](../../scripts/dump_prod_schema.py),
reconstructed from the system catalogs rather than by `pg_dump`.

**Why not `pg_dump`.** `supabase db dump` and `pg_dump` both need a direct
Postgres connection, which means `SUPABASE_DB_PASSWORD` — one of the two secrets
OPS-03 has been blocked on. The baseline was waiting on the credential and the
credential was waiting on somebody being able to say what the baseline would
contain. Reading the catalogs over the Management API needs only `SUPABASE_PAT`,
which was already in the shell, and it runs read-only by construction.

**When `SUPABASE_DB_PASSWORD` exists, `supabase db dump --schema public,private`
is the better generator** and this script should be retired in its favour. It is
a stopgap that broke a deadlock, not a thing to maintain forever.

**Not in it, on purpose:** Supabase-managed schemas (`auth`, `storage`,

**`ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin` is emitted commented out.**
`postgres` is not a member of that role, so those nine statements are real
production state that no migration can reproduce; they would abort the file on a
fresh project, and Supabase sets them at project creation anyway.

### Three things the first draft got wrong, because they will bite the next person

1. **Grants must come from `pg_class.relacl` / `pg_attribute.attacl`, never
   `information_schema`.** The `information_schema` views filter to grants the
   *querying* role can see. The Management API connects as a role that sees none
   of them, so `role_table_grants` returned **zero rows without erroring** and
   the first baseline shipped with an empty GRANTS section that looked fine.

2. **Column-level grants need their own section.** They do not appear in
   `role_table_grants` at all — which is precisely how the `organizations`
   `feature_flags` exposure (C1, live Stripe secret keys readable with the anon
   key) survived a month — and they are the entire mechanism of its fix. The
   baseline now carries the 15-column `SELECT` grant explicitly.

3. **Function and schema ACLs are load-bearing security, and were missing.** A
   function grants `EXECUTE` to `PUBLIC` by default and this database's default
   privileges add `anon`, `authenticated`, `service_role` on top. Two migrations
   exist for no other purpose than to take some of that back —
   `revoke_public_function_grants` (`20260815203919`) and
   `security_audit_revoke_trigger_fn_from_public` (`20260814183451`, the one with
   no file). A baseline that emits `CREATE FUNCTION` and stops describes
   production *with those two undone*, and a project rebuilt from it would come
   up with `enforce_publication_consent_provenance()` executable by `anon` again,
   silently. Schema `USAGE` on `private` was missing for the same reason; without
   it every RLS policy that calls a helper fails, which is every table.

The file is **deterministic** — two consecutive runs are byte-identical — so it
can be regenerated and diffed to see what changed in production. CRLF is
normalised out; 515 lines arrived with `CR` because `pg_get_functiondef` returns
stored source verbatim and some function bodies were applied from Windows-written
files before `.gitattributes` landed.

## The repair scripts

Written, validated, **not run**.

- [`reconcile_schema_migrations.sql`](reconcile_schema_migrations.sql) — inserts
  66 rows into `supabase_migrations.schema_migrations` and touches nothing else.
- [`reconcile_schema_migrations_rollback.sql`](reconcile_schema_migrations_rollback.sql)
  — deletes exactly those 66.

**66 = the 66 files whose stamp is nowhere in the history.** Six files are
excluded: five already have a row at their exact version (Table 1) and one has
the 8-digit stamp (2c).

**The baseline is not in the list**, and was until the integration suite proved
it could not live in `supabase/migrations/` at all — see "Where the baseline
lives" below. It is not a migration, `db push` never sees it, so it needs no
history row.

`created_by` is set to the marker `reconcile-ops-03`, which is what makes the
rollback exact — the 90 hand-applied rows carry an email and the 6 others carry
`NULL`, so neither can match. `statements` is `NULL`, which is honest: these
statements are not running now, and in most cases what ran already differed from
the file.

Both were validated against production before commit, read-only, by executing
each list as a `SELECT` over a literal constructor: **66 tuples, 66 distinct
versions, 0 colliding with an existing row.**

After the forward script, `supabase db push` sees **0 pending** and
`migrate-prod.yml`'s `max_pending` guard of 3 becomes correct as written — it
does not need raising. That guard exists to make the *unreconciled* state
unpushable; reconciling is what retires it, not a larger number.

### Why insert rows rather than rename the 64 files

Renaming each file to its recorded version is tidier and is the obvious move. It
is also how you apply 64 migrations to production by accident.

Perch stages a ticket by applying the migration files its PR **introduces** —
`git diff --name-only origin/main...HEAD -- '*supabase/migrations/*.sql'` — to a
database cloned from production, then the same list to production on merge. A
rename reads as a new file. Sixty-four renames inside a PR read as sixty-four new
migrations against a schema that already has them.

Repairing the history touches no files, so Perch never sees it.

## Where the baseline lives, and why it is not a migration

`supabase/baseline/20260909144435_baseline_20260909.sql`. **Not**
`supabase/migrations/`, which is where it was first committed and where the
brief asked for it.

It lived there for about an hour and broke the integration suite. The reason is
worth writing down, because it is the same reason the file exists:

`supabase start` replays the entire `supabase/migrations/` directory onto an
empty database — that is precisely the capability the baseline was meant to
provide. So the 72 incremental files built the schema, and then the baseline ran
and tried to `CREATE TYPE public.collaboration_status` a second time:

```
ERROR: type "collaboration_status" already exists (SQLSTATE 42710)
At statement: 15
```

**A migrations directory holding two complete descriptions of the same schema
cannot be replayed by anything.** Not `supabase start`, not `db push`, not a
staging rebuild. The baseline is a *replacement* for those 72 files, not an
addition to them, and until someone decides to actually retire them it has to
sit outside the directory.

Two ways this could have been "fixed" instead, both worse:

- **Make the baseline idempotent.** PostgreSQL has no `CREATE TYPE IF NOT
  EXISTS`, so every type, policy and constraint would need wrapping in a `DO`
  block. That is a lot of noise to make a file safely re-runnable *after* the
  migrations it supersedes — an order that should never happen.
- **Move the 72 files to `migrations-archive/` and let the baseline stand
  alone.** This is the real squash and is probably right eventually. It is also
  a large structural change that needs a decision, and deleting 72 files from
  that directory has the same Perch hazard as renaming them.

**Consequence for anyone standing up a fresh database:** `supabase start` gives
you the schema from the 72 incremental files, which is what CI uses today. The
baseline is for reading, for a staging project built deliberately from it, and
for diffing against a future regeneration to see what changed in production.
